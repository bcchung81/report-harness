    And then it got rejected

    멀쩡한 hwpx가 반입에서 반려됐다

    # 자료교환 시스템 판정 파일 : 보고서.hwpx 판정 : application/octet-stream ← hwpx로 인식하지 못함 사유 : 등록되지 않은 확장자

    변환기가 낸 패키지에 version.xml이 없었다. mimetype + container.xml만 있는 최소 OCF는 EPUB류와 지문이 같다 — 압축 내부까지 검사하는 반입 엔진이 hwpx로 판별하지 못한다. 같은 시스템에서 다른 hwpx는 정상 유통됐으니 시스템이 아니라 산출물 문제였다.

    The core split

    판단은 문서로, 실행은 스크립트로

    references/ — LLM이 읽는다

    style-guide.md 실보고서 34건 코퍼스
    md-profile.md 변환 가능 문법 + 린트 20종
    format-profile.kca.md 양식 실측 프로파일
    hwpx-recipe.md 변환 절차서
    rules-seed.md 회귀 규칙 70건

    scripts/ — 판단이 끼면 안 된다

    postprocess_hwpx.py 양식 정합 2,499줄
    validate_hwpx.py 구조·대조·수치
    lint_md_profile.py 초안 규격
    prep_report_md.py 변환 전 정규화
    consolidate_rules.py 규칙 통폐합

    양식 정합처럼 매번 똑같아야 하는 일은 전부 스크립트로 내려 LLM 편차를 없앴다. 판단이 필요한 일만 문서로 남겨 LLM이 읽게 한다.

    Four stages, one folder as the interface

    단계는 폴더를 읽고 쓴다

    단계입력산출물기계 시간
    ① research주제 · 제공자료 research/ + _manifest.jsonl—
    ② analyzeresearch/ · 기존 초안 05_analysis.md 논지 후보 · 근거 공백5분
    ③ draft05_analysis 10_outline.md → 20_draft.md10분
    ④ export승인된 20_draft final/{제목}.hwpx + 40_qa.md5분

    세션이 아니라 폴더가 맥락을 갖는다. 세션이 끊겨도 "이어서 해줘" 한 마디면 폴더 상태를 읽고 그 지점부터 잇는다 — 새 폴더를 만들지 않는다. 필요한 구간만 골라 진입할 수도 있다(자료가 있으면 ②부터, 초안이 있으면 ④만).

    The conversion is not the hard part

    변환기가 낸 hwpx는 아직 양식이 아니다

    # ④ export 실제 호출 순서 prep_report_md.py 정규화 — 모호한 입력은 exit 2로 거부 ↓ md → hwpx 생성 계층·표·이미지 마커 반영 ↓ postprocess_hwpx.py --all ★ 양식 정합 25스테이지 (여기가 본체) ↓ validate_hwpx.py structural OCF 시그니처·필수 멤버 roundtrip + compare 되읽어 내용 대조

    생성기는 계층과 표를 만들 뿐, 서체·간격·정렬·표 폭·머리말은 손대지 않는다. 후처리를 건너뛰면 규칙 위반본이 그대로 나간다.

    postprocess_hwpx.py — 2,499 lines

    hwpx XML을 직접 고치는 25스테이지

    star_footnotecaption_embedspacing zero_marginseffective_gapstable_alignment space_hierarchybody_justifyhighlight paren_smallsuperscript_starpage_margins center_cellstitle_boxtitle_box_topgap caption_table_fontdae_boldannex_banner sender_sizeheader_bannertable_pagination formula_boxline_fitlayout fit_page_width

    스테이지는 선언 테이블이다 — 각 항목이 (요약 키, 게이트, 실행, 발견 판정, 변경 판정)을 들고 있어 순서 제약이 코드가 아니라 데이터로 남는다. 예: caption_embed는 반드시 spacing 앞이다 — 캡션 문단이 hp:caption으로 들어가면서 사라지면 계층 전환 간격 계산이 통째로 달라진다.

    Example: what one stage actually does

    계층 간격은 '빈 문단'으로 만든다

    문단 여백으로 주면

    한컴이 인접 문단 여백을 합산·상쇄해 양식 실측값과 어긋난다
    검증도 스페이서 개수로는 못 한다

    양식 원형의 방식

    글자 크기를 줄인 빈 문단을 전환 지점마다 끼운다
    발신→□ 12pt · □→ㅇ 6pt · ＊→표 10pt

    # apply_spacing — 전환 지점을 찾아 스페이서 문단을 삽입/치환 TRANSITIONS[("sending","dae")] = 1200 HWPUNIT (12pt × 100) BLOCK_BOUNDARY_HEIGHT = 1500 두 번째 이후 □ 상단 # 콘텐츠 문단의 paraPr prev/next 여백은 0화 — 스페이서 단독 체계 유지

    이 값들은 기관 양식 바이너리를 뜯어 실측한 것이고, 프로파일 문서와 코드 상수가 어긋나면 테스트가 실패한다.

    R043 — the rejection, solved

    패키지를 한컴 정본 지문으로 맞춘다

    생성기 최소 패키지

    mimetype · container.xml
    content.hpf · header · section
    디렉터리 엔트리 3개 · 전량 STORED
    → EPUB류와 지문 동일

    canonicalize_package

    + version.xml hwpx 확정 마커
    + settings.xml · META-INF/manifest.xml · container.rdf
    − 디렉터리 엔트리 · Scripts/ 스텁
    엔트리 순서·압축 프로파일 정품 일치

    한글에서 재저장하면 빈 JScript 스텁(Scripts/headerScripts)이 삽입되는데, 확장자 없는 멤버 + application/x-javascript 등재라 이것도 반려 사유가 된다 — 함께 제거한다. 플래그와 무관하게 매 실행 적용되고 멱등이다. 구조 검증이 OCF 시그니처까지 확인해 회귀를 막는다.

    R042 — the bug that came from fitting exactly

    넘쳐서가 아니라 딱 맞아서 생긴 여백

    표 폭을 본문 폭과 정확히 같게 맞췄더니, 같은 문단에 선행 요소가 있으면 한컴 엔진이 표를 다음 줄로 내리면서 표 위에 15pt 빈 줄이 생겼다.

    30.29mmslack 0 — 제목표 상단
    25.02mmslack 283 hu 적용 후
    283 hu= 1.0mm · 문서 그리드 최소 단위

    사용자가 여섯 번 보고한 "제목표 위 여백"의 정체였다. 정적 XML로는 판정이 불가능해 실기동 픽셀 계측으로 잡았다. 표를 줄일 때 내부 그림의 scaMatrix·rotationInfo 파생 캐시도 함께 재계산한다 — 안 하면 도너 원본 값이 남아 조용히 어긋난다.

    Verification, three layers

    조용히 틀린 걸 내주지 않는다

  • 구조
    validate_hwpx structural — OCF 시그니처(첫 엔트리 mimetype·STORED·offset 0), 필수 멤버, 디렉터리 엔트리 부재
  • 왕복
    hwpx를 다시 md로 되읽어 compare로 내용 대조. 어긋나면 2회까지 재변환
  • 수치
    validate_hwpx numbers — 초안의 수치를 조사 폴더와 대조해 근거 없는 값을 잡는다
    • # assert_postprocess — 침묵 실패 차단. 후처리는 대상 0건이어도 exit 0이다 title_box.found must be True sender_size.runs_changed == 1 dae_bold.runs_changed == md의 □ 개수 table.column_width_inverted == 0 열 폭이 내용과 역행하지 않는가

    그래도 어긋난 게 남으면 목록을 밝힌 뒤 마크다운 초안을 넘긴다. 틀린 hwpx를 조용히 내주는 것보다 낫다. 추가로 PostToolUse 훅이 hwpx 생성을 감지하면 구조 검증을 강제 실행한다 — 모델의 협조 없이 걸리는 마지막 안전망이다.

    The web version owns the whole conversion

    MCP 없이 자립하는 변환기

    md
    parsemd-profile 서브셋
    rendersection0.xml 직접 조립
    동결 header.xmlcharPr 44 · paraPr 34 · borderFill 30
    .hwpx

    검증된 산출물에서 header.xml(93KB)만 뽑아 자산으로 동결하고, 생성기는 고정 id를 참조하는 section0.xml만 쓴다. 스타일 id 맵은 실측 확정값이다 (□ = paraPr 8 / charPr 11, ㅇ = 9 / 0 볼드, ※ = 20 / 13 …).

    열 폭도 다시 짰다. 기존 변환기는 34폭 열에 18.3mm를 줘서 4줄로 깨졌는데, 셀 표시폭 기반으로 하한(헤더 폭·8폭)·상한(전체의 40%)을 클램프하고 비례 재분배해 2줄로 떨어뜨린다.

    Compounding

    같은 지적을 두 번 받으면 규칙이 된다

    게이트 피드백
    lessons 1줄
    2회 반복
    규칙 승격
    프리플라이트 자동 적용

    규칙에는 단계 태그([research]·[draft]·[export])가 붙고, 각 단계는 grep으로 자기 태그만 읽는다. 첫 실행 때 시드 70건이 복사돼 출발점이 된다. 승격된 규칙 중 상당수는 스크립트·린트로 내려가 텍스트 규범이 아니라 기계 검사가 된다.

    Accumulation eats itself

    75→ 35 1줄 자수 · 검증 없는 추정 → SVG 렌더 실측
    (중앙값 35 · 최대 47)

    그 규칙이 넉 달을 살아 있었다. 전 문서가 한 문단 3~4줄로 늘어졌고 쪽수가 두 배가 됐다.

    규칙이 안 지켜져서 난 사고가 아니다. 틀린 규칙이 아주 성실하게 지켜져서 난 사고다. 규칙이 두 달에 43건까지 늘자 길어서 안 읽히고, 안 읽히니 안 지켜지고, 그래서 같은 실수가 또 박제됐다.

    Research: contract, not method

    조사는 방법을 강제하지 않는다

    # research/fetched/{주제}/{자료}.md — 프론트매터 필수 source_url: https://example.go.kr/notice/123 fetched_at: 2026-07-22T10:31:00+09:00 tool: WebFetch confidence: 확정 원출처 직접 대조 가능 / 아니면 추정 # 같은 내용을 _manifest.jsonl 에 산출물 1건당 1줄 append

    어떤 도구로 조사하든 상관없다 — 환경에 있는 걸 골라 쓰고 없으면 건너뛴다. 강제되는 건 산출물이 계약대로 쌓이는 것뿐이다. 그래서 도구가 하나도 없어도 파이프라인이 멈추지 않는다. 원문 발췌로 수집하고(의역 금지), 이미 확보한 근거는 다시 조사하지 않는다.

    "이 숫자 어디서 나왔냐"

    근거를 다섯 지점에서 붙든다

    지점무엇을 하나
    조사산출물마다 원출처 프론트매터 + manifest. 출처 불명 자료는 아예 적재하지 않는다
    위키 인용원출처가 추적되면 [확정], 위키에만 있으면 [미확정]
    초안초안의 수치를 조사 폴더와 대조해 근거 없는 값을 잡아낸다
    변환구조 검증 + 왕복 대조. 어긋난 게 남으면 조용히 내주지 않는다
    회귀같은 지적이 반복되면 규칙으로 승격돼 다음 보고서에 자동으로 걸린다

    옮기는 수고를 줄이려고 시작했는데, 줄이고 보니 남는 게 하나 더 있었다 — 근거가 문서에 붙어서 나온다. 손으로 옮길 때는 출처가 중간에 떨어져 나갔다.
